# 【架构思考】AI 陪伴场景下的 Message ID 与 MongoDB 分片设计

AI 陪伴业务会持续产生大量聊天消息。存储设计需要同时满足：

- 按用户查询最近聊天记录；
- 通过 Message ID 点查单条消息；
- 单个用户的长期数据可以拆分到不同 Chunk 和 Shard；
- 保持 ID 和数据模型简单，避免把过多业务语义编入 ID。

使用 UUIDv7 作为 Message ID，并通过 `user_id + bucket_month` 完成数据分片。

## 一、整体方案

### 1. Message ID

MongoDB 文档的 `_id` 使用 UUIDv7。数据库内按标准 BSON Binary Subtype 4 存储为 16 字节，对外则使用 36 位标准 UUID 字符串作为 `message_id`。

```javascript
{
  _id: UUID("019fccc5-1895-7abc-8def-123456789abc")
}
```

UUIDv7 底层为 16 字节，核心结构为：

```text
48 bits Unix 毫秒时间戳
+ UUID 版本与变体位
+ 74 bits 随机或单调序列数据
```

它是 [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html) 定义的通用标准，不依赖 MongoDB，可在写库前由任意业务实例并发生成。UUIDv7 同时满足分布式唯一性、毫秒时间可解析和按时间趋势有序的需求，无需再额外编入 userId、HMAC、业务类型或物理 Shard 信息。

业务类型、子类型、消息状态等信息应作为独立文档字段存储，不与 Message ID 耦合。

### 2. 分片键

`message_log` 使用复合 Shard Key：

```javascript
{
  user_id: "hashed",
  bucket_month: 1
}
```

`bucket_month` 是根据消息创建时间计算出的 UTC 自然月：

```text
2026-01 -> 202601
2026-08 -> 202608
```

这个设计将数据分布粒度从“单个用户”细化为“单个用户 + 单个月份”。MongoDB 因此可以将同一用户不同月份的数据分配到不同 Chunk，并由 Balancer 在 Shard 之间迁移。

> `bucket_month` 增加了可拆分性，但不保证同一用户的不同月份一定分布到不同物理 Shard。实际位置由 MongoDB 的 Chunk 分裂和 Balancer 决定。

### 3. 文档结构

```javascript
{
  _id: UUID("019fccc5-1895-7abc-8def-123456789abc"),
  user_id: "user-uuid",
  bucket_month: 202608,
  c_time: ISODate("2026-08-04T12:34:56.789Z"),

  biz_code: "message",
  sub_biz_code: "text",
  content: "..."
}
```

字段职责：

| 字段             | 职责                                 |
| ---------------- | ------------------------------------ |
| `_id`          | MongoDB 主键，同时作为`message_id` |
| `user_id`      | 用户归属与 Shard Key 前缀            |
| `bucket_month` | 月份分桶与 Shard Key 后缀            |
| `c_time`       | 权威的毫秒级消息创建时间             |
| `biz_code`     | 稳定的一级业务类型                   |
| `sub_biz_code` | 稳定的子业务类型                     |

## 二、统一的消息创建函数

消息写入必须通过统一函数构造数据库文档。该函数只获取一次当前时间，再从同一个 `now` 生成 UUIDv7 `_id`、`bucket_month` 和 `c_time`。

```text
now = 当前 UTC 时间，保留毫秒

_id          = UUIDv7FromTimestamp(now)
bucket_month = now.Year * 100 + now.Month
c_time       = now
```

推荐使用 [`github.com/gofrs/uuid/v5`](https://pkg.go.dev/github.com/gofrs/uuid/v5)。该库支持传入指定时间生成 UUIDv7，避免生成 ID 和计算月桶时多次读取系统时钟。

Go 示例：

```go
type MessageBase struct {
	ID          primitive.Binary `bson:"_id"`
	UserID      string           `bson:"user_id"`
	BucketMonth int              `bson:"bucket_month"`
	CTime       time.Time        `bson:"c_time"`
}

func NewMessageBase(userID string) (MessageBase, string, error) {
	now := time.Now().UTC().Truncate(time.Millisecond)
	id, err := uuid.NewV7AtTime(now)
	if err != nil {
		return MessageBase{}, "", err
	}

	doc := MessageBase{
		ID: primitive.Binary{
			Subtype: 0x04,
			Data:    id.Bytes(),
		},
		UserID:      userID,
		BucketMonth: now.Year()*100 + int(now.Month()),
		CTime:       now,
	}

	return doc, id.String(), nil
}
```

这样可以保证：

- `_id`、`bucket_month` 和 `c_time` 始终来自同一个时间点；
- UUIDv7 和 `c_time` 均保留毫秒精度；
- 在秒边界和月边界不会因多次读取系统时钟而产生不一致；
- 业务可以在写入 MongoDB 之前获取 `message_id`，用于幂等、日志和消息队列事件。

## 三、MongoDB 分片配置

对于已有数据的 Collection，先创建 Shard Key 索引：

```javascript
db.message_log.createIndex({
  user_id: "hashed",
  bucket_month: 1
})
```

然后执行分片：

```javascript
sh.shardCollection(
  "database_name.message_log",
  {
    user_id: "hashed",
    bucket_month: 1
  }
)
```

Shard Key 索引主要用于数据分布和查询路由。历史消息分页需要额外的业务索引：

```javascript
db.message_log.createIndex({
  user_id: 1,
  bucket_month: 1,
  c_time: -1,
  _id: -1
})
```

## 四、查询方案

### 1. 根据 userId 和 messageId 点查

业务接口查询消息时，必须同时携带 `userId` 和 `messageId`。

后端解析 UUIDv7 中的 UTC 毫秒时间，计算 `bucket_month`：

```text
messageId -> UUIDv7 timestamp -> UTC year/month -> bucket_month
```

Go 解析示例：

```go
func ParseMessageID(messageID string) (primitive.Binary, time.Time, int, error) {
	id, err := uuid.FromString(messageID)
	if err != nil {
		return primitive.Binary{}, time.Time{}, 0, err
	}

	timestamp, err := uuid.TimestampFromV7(id)
	if err != nil {
		return primitive.Binary{}, time.Time{}, 0, err
	}

	createdAt, err := timestamp.Time()
	if err != nil {
		return primitive.Binary{}, time.Time{}, 0, err
	}
	createdAt = createdAt.UTC()

	binaryID := primitive.Binary{
		Subtype: 0x04,
		Data:    id.Bytes(),
	}
	bucketMonth := createdAt.Year()*100 + int(createdAt.Month())

	return binaryID, createdAt, bucketMonth, nil
}
```

然后使用完整 Shard Key 查询：

```javascript
db.message_log.findOne({
  _id: UUID(messageId),
  user_id: userId,
  bucket_month: bucketMonth
})
```

`user_id + bucket_month` 负责将查询路由到相关 Shard，`_id` 负责在目标 Shard 内完成主键点查。

`userId` 必须来自已认证的用户上下文，不能只信任客户端传入值。它同时承担用户数据边界校验的职责。

### 2. 查询最近消息

查询当月消息：

```javascript
db.message_log.find({
  user_id: userId,
  bucket_month: 202608
})
.sort({ c_time: -1, _id: -1 })
.limit(100)
```

如果当月数量不足，再查询上一个月份。因此，“最近 50 轮对话”通常只需要访问一个月桶，月初或低频用户可能访问两个月桶。

不应将 UUIDv7 的字典序当作业务上的严格全局时序。UUIDv7 在毫秒粒度上趋势有序，但不同进程在同一毫秒生成的 ID 不保证符合真实事件先后顺序。`c_time + _id` 共同作为稳定排序和分页游标。

## 五、设计边界

### 1. 月桶不是物理分表

`bucket_month` 是 Shard Key 的一部分，不代表每个月创建一个 Collection。在线数据默认全部保存在同一个 `message_log` Collection 中，由 MongoDB 根据 Shard Key 管理 Chunk 和数据分布。

### 2. 单用户单月仍是最小聚合单元

相同 `user_id + bucket_month` 的文档具有相同的完整 Shard Key 值，不能再根据这个 Shard Key 拆分。

因此需要监控：

- 单用户单月消息数量和总字节数；
- Shard 存储、QPS 和写入延迟的倾斜程度；
- Jumbo Chunk 和 Balancer 迁移情况。

如果真实数据证明单用户单月仍然过大，再评估日桶或额外子桶。不在没有实际数据前提下提前增加查询扩散和实现复杂度。

### 3. UUIDv7 时间不是权威业务时间

UUIDv7 可以由客户端或导入程序按任意时间生成。正常在线写入必须使用统一创建函数，历史数据回灌则必须使用消息的原始业务时间同步构造 `_id`、`bucket_month` 和 `c_time`。`c_time` 仍然是权威业务时间，UUIDv7 时间用于路由推导、排障和趋势排序。

## 六、未来的 Archive 备注

Sharding 解决数据分布和水平扩展问题，Archive 解决旧数据长期占用高成本在线存储的问题。两者的目标不同。

第一阶段不实现 Archive，所有消息保存在分片后的 `message_log` 中。后续根据以下数据决定是否归档：

- 每月数据增长量；
- MongoDB 存储、备份和副本成本；
- 三个月以前消息的实际查询率；
- 历史消息允许的查询延迟。

如需归档，可按完整自然月将数据迁移到独立的低成本 MongoDB 集群，或者 S3、OSS、TOS 等对象存储。归档流程必须遵循：

```text
幂等复制 -> 数量与校验和验证 -> 记录归档水位 -> 分批删除热数据
```

Archive 是未来的成本优化手段，不影响当前 `UUIDv7 + user_id/bucket_month Shard Key` 的核心设计。
