# 数据库选型

## 1. 结论先行

- 通用互联网业务默认选择 PostgreSQL。
- MongoDB 适合有界、嵌套、整体读写的文档。
- ClickHouse 适合批量追加和海量分析。
- 不因“大公司不用外键或 JOIN”就否定 PostgreSQL。
- 不在缺少数据证明时提前引入多套数据库。

## 2. 三种数据库的区别

| 区别             | PostgreSQL                               | MongoDB                                                  | ClickHouse                                                                      |
| ---------------- | ---------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 核心定位         | OLTP 通用业务主库                        | 文档数据库                                               | OLAP 分析数据库                                                                 |
| 存储模型         | 以行存储为主                             | BSON 文档                                                | 列式存储                                                                        |
| 适合的数据       | 结构化数据及实体关系                     | 有界、嵌套的完整文档                                     | 大规模明细和分析事件                                                            |
| 主要写入方式     | 单条或批量事务写入                       | 单文档写入、批量写入                                     | 批量追加写入                                                                    |
| 主要查询方式     | 点查、范围查询、关联和聚合               | 按文档整体读取                                           | 大范围扫描和聚合                                                                |
| 更新与删除       | 适合频繁、精确更新                       | 适合单文档内原子更新                                     | 不适合频繁更新和删除                                                            |
| 事务能力         | 完整 ACID，多行、多表事务成熟            | 支持事务，单文档原子操作最自然                           | 事务能力有限                                                                    |
| 数据约束         | 主键、唯一、外键、类型和检查约束         | 支持 Schema 校验和唯一索引，约束相对灵活                 | 不以唯一性和关系约束为核心                                                      |
| Schema           | 结构明确，也可使用 JSONB                 | 灵活，不同文档可以有不同结构                             | 建表时明确列结构                                                                |
| 对大宽表是否友好 | 一般，行越宽，整行读取和存储成本越高     | 较友好，适合字段较多、结构灵活的文档，但受单文档大小限制 | 友好，设计成大宽表没有问题。<br />查询少量列时优势明显，但`SELECT *` 成本较高 |
| 关系查询         | JOIN 能力强                              | 支持关联查询，但不是主要优势                             | 支持 JOIN，但更适合分析场景                                                     |
| 水平扩展         | 原生分片能力较弱，通常依赖扩展或业务拆分 | 原生支持分片                                             | 原生支持分布式表和集群                                                          |
| 典型场景         | 用户、订单、支付、额度和业务状态         | 内容文档、角色配置、大规模消息文档                       | 日志、指标、Token 消耗和行为分析                                                |
| 不适合的场景     | 超大规模分析扫描                         | 复杂关系和大量多实体事务                                 | 高频单条 CRUD 和强事务业务                                                      |





## 3. 为什么 PostgreSQL 适合作为默认主库

- 不使用外键和 JOIN 后，PostgreSQL 仍有事务、唯一约束、类型约束等优势。
- JSONB 可以承载动态数据。
- 查询方式变化时，SQL 的适应性更强。
- 单库阶段的架构和运维成本最低。
- 默认选择 PostgreSQL，不等于所有数据都永久存放在 PostgreSQL 中。
