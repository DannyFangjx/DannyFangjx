# 从 Logstash 到 Flink + Vector：聊聊日志系统和实时数据平台的演进

最近在排查公司 Elasticsearch 集群问题的时候，顺着日志链路、ES 存储、Flink 实时计算一路研究下来，对日志平台和实时数据平台有了一些新的理解。

这篇文章记录一下自己的思考。

---

# 一、很多团队最初的架构

最经典的日志架构大概长这样：

```text
业务服务
    ↓
Kafka
    ↓
Logstash
    ↓
Elasticsearch
```

或者：

```text
业务服务
    ↓
日志文件
    ↓
Filebeat
    ↓
Logstash
    ↓
Elasticsearch
```

这套架构已经存在很多年了。

很多公司都是这么起步的。

---

# 二、Logstash 到底解决了什么问题

很多人觉得：

> Logstash 不就是把日志写入 ES 吗？

其实并不是。

Logstash 本质上是一个：

```text
数据采集
数据转换
数据缓冲
数据转发
```

平台。

它解决了几个非常重要的问题。

---

## 1. 解耦业务和 ES

如果没有 Logstash：

```text
业务服务
    ↓
直接写 ES
```

那么：

* ES 变慢，业务跟着变慢
* ES 升级，业务要改代码
* ES 故障，业务可能受影响

而有了 Logstash：

```text
业务
 ↓
Kafka
 ↓
Logstash
 ↓
ES
```

业务只需要发送 Kafka。

后面的事情交给 Logstash。

---

## 2. Bulk 批量写入

这是 Logstash 最重要的价值之一。

很多新人误以为：

```text
日志一条一条写 ES
```

实际上不是。

ES 最推荐的写入方式是：

```text
Bulk API
```

例如：

```text
1000条日志
 ↓
一次 HTTP 请求
 ↓
ES
```

而不是：

```text
1000条日志
 ↓
1000次 HTTP 请求
```

Logstash 内部会自动帮我们完成 Bulk 聚合。

---

## 3. 数据转换

例如：

业务日志：

```json
{
  "uid": 1001
}
```

经过 Logstash：

```json
{
  "user_id": "1001",
  "@timestamp": "2026-06-05"
}
```

还能：

* 时间格式转换
* 字段重命名
* 数据脱敏
* 数据过滤

---

# 三、为什么越来越多人不用 Logstash 了

随着数据量增长，Logstash 的问题也逐渐暴露。

最主要原因：

```text
Java
资源占用高
内存占用大
```

很多场景下：

```text
Logstash
2~4GB 内存
```

属于正常现象。

于是越来越多公司开始转向：

```text
Vector
```

---

# 四、Vector 是什么

Vector 可以理解成：

```text
现代版 Logstash
```

它是 Rust 开发的。

官方定位：

```text
High-performance observability data pipeline
```

高性能可观测性数据管道。

---

## Vector 的优势

### 1. 非常省资源

同样处理：

```text
10000 条日志 / 秒
```

可能：

```text
Logstash
3GB 内存
```

而：

```text
Vector
300MB 内存
```

就够了。

---

### 2. 性能更高

Rust 带来的性能优势非常明显。

特别是在：

```text
日志采集
日志转发
日志清洗
```

场景。

---

### 3. 更适合云原生

很多 Kubernetes 环境已经开始：

```text
FluentBit
Vector
```

替代：

```text
Logstash
```

---

# 五、但 Vector 解决不了所有问题

这里是很多人的误区。

Vector 负责的是：

```text
搬运
```

而不是：

```text
计算
```

例如：

```text
今天 DAU 是多少？
```

Vector 不负责。

---

# 六、Flink 的出现

Flink 是另一类产品。

如果说：

```text
Vector = 搬运工
```

那么：

```text
Flink = 实时计算引擎
```

---

# 七、Flink 到底在算什么

例如：

用户发消息：

```json
{
  "user_id": 1001,
  "msg": "hello"
}
```

进入 Kafka。

---

Flink 实时统计：

```text
今日 DAU

在线人数

消息数

Token 消耗

订单金额

GMV

机器人活跃度
```

---

然后写入：

```text
Redis
ClickHouse
MySQL
```

---

# 八、为什么 Flink 非常有价值

假设老板问：

```text
现在 DAU 是多少？
```

如果直接查数据库：

```sql
select count(distinct user_id)
```

可能需要：

```text
几十秒
几分钟
```

甚至拖垮数据库。

---

而 Flink 的思路是：

用户每产生一条行为：

```text
实时计算
实时累计
实时更新
```

最终：

```text
Redis:
DAU=123456
```

后台打开就是秒返回。

---

# 九、现代日志和数据平台架构

很多公司正在从：

```text
Kafka
 ↓
Logstash
 ↓
ES
```

演进为：

```text
Kafka
 ↓
Vector
 ↓
ES
```

负责日志查询。

---

同时：

```text
Kafka
 ↓
Flink
 ↓
ClickHouse
```

负责实时分析。

---

整体架构：

```text
业务服务
        ↓
      Kafka
        ↓

 ┌─────────────┐
 │   Vector    │
 └─────────────┘
        ↓
        ES

 ┌─────────────┐
 │    Flink    │
 └─────────────┘
        ↓
 ClickHouse
 Redis
```

对于 AI Agent、聊天机器人、AI 社交产品来说，这套架构特别有价值。

例如：

实时统计：

Token 消耗

模型调用次数

机器人活跃度

用户消息数

礼物收入
```

这些指标天然适合：

```

来处理。

# 十一、总结

我的理解是：

Logstash、Vector、Flink 其实是三个不同层面的东西。

Logstash：

```text
日志采集平台
```

Vector：

```text
高性能日志管道
```

Flink：

```text
实时计算平台
```

未来的数据平台趋势大概率会是：

```text
Kafka
 ↓

Vector
 ↓
ES

+

Flink
 ↓
ClickHouse
```

日志查询交给 ES。

实时统计交给 Flink + ClickHouse。

这也是目前越来越多互联网公司的主流选择。


个人单枪匹马，怎么选？
既然是你一个人撸业务，架构演进可以遵循 “实用至上” 的原则：

初期（0 -> 1）：继续用 Redis + Prometheus

如果目前只是看个大盘趋势（总 DAU、当前在线人数），Flink 对你来说属于过度设计（Overengineering）。

一个人去运维 Flink + ZooKeeper/Kubernetes + Kafka，会吃掉你大量的精力。

中后期（1 -> 10）：引入 Flink (尤其是 Flink SQL)

当产品经理开始跟你要各种细分报表（如：“看下昨天从抖音渠道进来的、18-25岁用户的次留和充值转化率”），或者 Redis 内存吃紧、主业务被统计逻辑拖慢时。

这时候可以用 Flink SQL。现在 Flink SQL 已经非常成熟，写流处理就像写 MySQL 语句一样，一个人也能快速上手，把计算好的报表数据拍进 ClickHouse 里，出报表体验极佳。
